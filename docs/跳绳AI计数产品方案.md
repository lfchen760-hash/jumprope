# 儿童跳绳 AI 计数产品方案（对标「天天跳绳」）

> 目标：用手机/平板摄像头实时识别孩子跳绳动作，自动计数，并围绕「孩子爱跳、家长能看」做一整套产品。

---

## 1. 结论先行

| 决策点 | 推荐 |
|---|---|
| 计数方式 | **摄像头人体姿态识别为主 + 麦克风落地声为辅（交叉校验）** |
| 推理位置 | **端侧（手机本地）推理**，只上传结果和少量抽帧，不上传视频 |
| 首选落地形态 | **微信小程序**（家长/学校生态）+ 一套 Web 版做快速验证 |
| 核心模型 | MediaPipe Pose Landmarker（BlazePose，33 关键点）或 MoveNet Thunder（17 关键点） |
| 计数算法 | 髋部垂直位移 → 尺度归一化 → One Euro 滤波 → 迟滞状态机计数 |
| 最大技术风险 | 弱光/逆光、跳跃出画、多人入镜、运动模糊导致漏计或误计 |

一句话：**先用 Web + MediaPipe 在两周内把「准确率」这个唯一生死指标验证掉，再谈产品功能。**

---

## 2. 为什么选摄像头姿态识别

儿童跳绳计数的可选技术路线：

| 方案 | 准确率 | 成本 | 儿童可用性 | 结论 |
|---|---|---|---|---|
| **摄像头姿态识别** | 高（可做到 97%+） | 零硬件 | 手机架起来即可 | ✅ 主方案 |
| 麦克风落地声检测 | 中（噪声环境差） | 零硬件 | 好 | ✅ 辅助校验 |
| 手机加速度计 | 中高 | 零硬件 | ❌ 孩子不会把手机揣兜里 | 仅成人场景 |
| 智能跳绳（IMU/霍尔） | 最高 | 需买硬件 | 好但门槛高 | 后期可接入 |
| 人工手动点按 | 100% | 零 | 家长嫌麻烦 | 仅兜底 |

摄像头方案的关键优势：**零硬件成本、能顺便做动作质量分析和防作弊**，也是「天天跳绳」的核心体验。

### 技术选型

- **Web 验证版**：React + TypeScript + Vite，`@mediapipe/tasks-vision`（WASM + GPU delegate）
- **小程序**：原生小程序 `camera` 组件 + `CameraContext.onCameraFrame` 拿到 RGBA 帧，喂给 WASM/WebGL 推理；模型从 CDN 动态下发并本地缓存（注意小程序包体积限制）
- **原生 App（后期）**：iOS `Vision` 人体姿态 / Android `ML Kit Pose Detection`，性能最好
- **后端**：NestJS 或 Go，PostgreSQL + Redis，对象存储放抽帧证据

> 模型体积参考：Pose Landmarker Lite 约 5–6 MB，必须做 CDN 分发 + 强缓存 + 首屏进度提示，否则首次进入体验很差。

### 3.5 为什么不是 YOLO？（模型选型的常见疑问）

**结论：核心计数不用 YOLO，但 YOLO 式的「人体检测器」其实已经在你用的模型里了。**

**1）YOLO 给的是检测框，我们需要的是一条关键点轨迹**

计数依赖髋部（或脚踝）在垂直方向的周期位移，需要的是**关键点坐标**。检测框只能给出人形外接矩形，框的下沿会随手臂摆动、腿部张开不断变化，抖动远大于髋部关键点，用它做峰值检测会大量误计。

**2）MediaPipe 内部就是「检测器 + 关键点回归」两阶段**

BlazePose 的管线是：先用一个轻量人体检测器（SSD 变体）框出人，再裁剪送进关键点回归网络。**这就是 YOLO 所在的位置**，只不过被换成了一个更小、更专门为姿态任务优化的检测器。所以「用检测器找人」这一步并没有被跳过，而是内置了。

**3）带关键点的 YOLO 也确实存在，叫 YOLO-Pose**

YOLOv8-pose / YOLO11-pose / RTMPose 都是「一次前向同时出框 + 17 个 COCO 关键点」，属于**多人姿态估计**。它们的优势场景是：

- **一屏多人**（体育课、班级赛、家庭同框）——MediaPipe 单次只稳定输出一个人
- 需要**自己标注数据微调**（孩子身高分布、特殊服装）
- 部署在**服务端 GPU** 做批量视频复盘

**4）但在手机端，YOLO 的工程代价明显更高**

| | MediaPipe Pose | YOLO-Pose | RTMPose |
|---|---|---|---|
| 关键点 | 33（含脚趾、脚踝、朝向） | 17（COCO） | 17 / 26 |
| 手机端加速 | ✅ 内置 GPU delegate，开箱即用 | ❌ 需转 ncnn / MNN / TFLite | ⚠️ 需 ONNX Runtime / ncnn |
| 小程序可用性 | 好（WASM + WebGL） | 差（包体、算子兼容性） | 一般 |
| 多人 | 弱（需自己加跟踪） | 强（原生多人） | 强 |
| 训练/调参成本 | 低 | 中（要准备数据集） | 中 |

对一个「一个孩子对着手机跳」的产品，**MediaPipe 综合性价比最高**。YOLO 在这个场景里的精度提升几乎体现不出来，反而把工程量翻倍。

**5）为什么不直接检测「绳子」？**

很多人第一反应是「检测绳子转了几圈」。这条路很脆弱：

- 绳子是**细长高速物体**，30fps 下每帧位置跳变极大，运动模糊严重
- 绳子会被身体大面积遮挡，遮挡期间完全丢失
- 绳子转速约 2–3 圈/秒，30fps 采样不足，容易出现**混叠**，圈数直接数错
- 换个绳子颜色/材质，模型就得重新标

**判定身体、而不是判定绳子**，才是稳的做法，也是主流跳绳 App 的选择。

**6）演进建议**

- P0–P2（单人对摄像头）：**MediaPipe Pose，不加 YOLO**
- P4（多人同屏 / 班级赛）：引入 **YOLO-Pose 或 RTMPose + ByteTrack** 做多人跟踪，每人一条计数流水线
- 需要人体框做「入画引导」时，用模型自带的检测器即可，不必单独上 YOLO

## 4. 核心：计数算法

这是整个产品唯一的技术壁垒，必须做扎实。

### 4.1 信号提取

每帧拿到 33 个归一化关键点（BlazePose 索引：11/12 肩、23/24 髋、27/28 踝）。

```js
const hipY   = (lm[23].y + lm[24].y) / 2;          // 髋部中点，y 向下为正
const shY    = (lm[11].y + lm[12].y) / 2;
const torso  = Math.abs(hipY - shY) || 1e-3;        // 躯干长度，用于尺度归一化

const lift = -(hipY - baselineY) / torso;           // 抬起为正，且与身高/距离无关
```

**关键点：必须用躯干长度做归一化**。否则手机离得远、孩子个子矮，位移阈值就失效了——这是新手最容易踩的坑。

`baselineY` 来自**开场 2–3 秒的静态标定**：提示「请自然站好」，取中位数作为站立基线。

### 4.2 滤波

原始关键点抖动很大（尤其 Lite 模型），直接做峰值检测会疯狂误计。

- 首选 **One Euro Filter**：低速时强平滑、高速时低延迟，非常适合跳绳这种 1.5–3 Hz 的周期性动作。
- 备选：5 点滑动平均，实现简单但延迟高约 80ms。

### 4.3 计数状态机（不要用裸峰值检测）

```js
const H  = 0.05;      // 迟滞阈值（躯干比例，约等于起跳 5% 身高）
const MIN_DT = 180;   // ms，最快 333 次/分，超过必然是抖动手误计

let state = 'GROUND';
let lastCountAt = 0;

function onFrame(lift, t) {
  if (state === 'GROUND' && lift >  H && t - lastCountAt > MIN_DT) {
    state = 'AIR';
  } else if (state === 'AIR' && lift < -H * 0.6) {
    state = 'GROUND';
    if (t - lastCountAt > MIN_DT) {
      lastCountAt = t;
      emitCount();                 // 一个完整「起跳 + 落地」周期记 1 次
    }
  }
}
```

用**迟滞双阈值（hysteresis）**而不是固定阈值，是为了防止信号在阈值附近抖动导致一次跳绳被记成好几次。

### 4.4 抗错处理（决定成败的细节）

| 问题 | 对策 |
|---|---|
| 关键点置信度低 | 低于阈值时保持上一状态，最多插值 100–150ms，超时则暂停计数并在 UI 提示 |
| 掉帧 / 时间戳不准 | 用 `requestVideoFrameCallback` 的 `mediaTime` 作为时间基准，不要用 `performance.now()` |
| 多人入镜 | 取 bbox 面积最大的人体；检测到 >1 人时提示「画面里只能有一个人哦」 |
| 跳出画面 | 脚踝/髋部越界时暂停计数，UI 引导回框内 |
| 半身入镜 | 检测不到脚踝时退化为「髋部 + 肩膀」信号，并在质量分里扣分 |
| 起跳幅度太小（偷懒跳） | 结合膝关节角度变化辅助判定，幅度过小不计数 |
| 主线程卡顿 | 推理放 Web Worker / OffscreenCanvas，UI 线程只做渲染 |

### 4.5 麦克风辅助校验（可选但推荐）

检测落地「咚」声：短时能量 + 谱通量峰值检测，与视觉计数做**时间对齐**。

- 两路都命中 → 计数 +1，置信度高
- 只有视觉命中 → 计数 +1 但标记低置信
- 只有声音命中 → 不计（可能是旁边有人拍球）

这个交叉校验能把误计率压下去一大截，而且几乎不增加成本。

### 4.6 必须做的事：离线评测集

**在上线前，先花 3 天做这件事：**

1. 采集 30–50 段真实视频：不同孩子身高、不同光照（顺光/逆光/夜间灯）、不同距离（1.5–3m）、不同角度、不同帧率（30/60fps）、iPhone/安卓各若干。
2. **人工逐段标注真实次数**。
3. 写一个离线脚本跑完整算法，输出每段的 **MAE / 绝对误差率**。
4. 目标是 **30 秒 100 次以内误差 ≤ 2 次**，即准确率 ≥ 98%；低于 95% 不要进入产品开发。

这个评测集是后面所有算法迭代的回归测试基线，**必须建**。

## 5. 数据模型

```sql
-- 孩子档案
child(id, parent_id, name, birthday, height_cm, weight_kg, avatar_url, created_at)

-- 单次训练
session(
  id, child_id, start_at, duration_sec,
  count, avg_rate, max_rate, calories,
  source,              -- camera / manual / device
  quality_json,        -- {fps, dropRate, confidence, lightScore}

-- 每日汇总

-- 班级 / 好友
group(id, name, owner_id), group_member(group_id, child_id, role)
```

**排行榜**用 Redis ZSET：日榜 / 周榜 / 班级榜，`ZINCRBY` 天然适合。

## 6. 儿童向产品设计（这才是留存的关键）

技术只决定「能不能用」，产品决定「孩子愿不愿意天天用」。

**孩子端**
- 语音实时报数 + 鼓励（「再来 10 个就破纪录啦！」）
- 虚拟形象/成长树：跳绳次数养宠物、种树
- 勋章体系：连续打卡 7 天、单次 200 个、1 分钟 150 个
- 每日目标 + 进度环，完成后放烟花动画
- 短时高频：单次默认 1 分钟，避免孩子疲劳
- 护眼/防沉迷：连续使用 15 分钟强制休息提示

**家长端**
- 训练报告：次数、时长、频率曲线、卡路里
- 目标设置、使用时长管控
- 视频抽帧回看（可选，注意隐私）
- 微信推送：孩子完成今日目标

**社交/竞技**
- 班级 PK、好友约战、家庭赛
- ⚠️ 排行榜要按年龄段/身高分组，否则低龄孩子永远垫底，会直接劝退

## 7. 防作弊（做排行榜就必须有）

孩子的「作弊」动机比想象中强，而且家长也在意公平。

| 规则 | 说明 |
|---|---|
| 计数必须来自摄像头模式 | 手动模式成绩不进排行榜 |
| 频率异常 | > 250 次/分持续 10 秒 → 标记 suspicious |
| 人体在场检测 | 全程检测不到人体 → 无效 |
| 多人检测 | 画面中 > 1 人 → 无效 |
| 随机抽帧 | 每次训练随机抽 ≤3 帧上传，人工/模型抽检 |
| 视频重复检测 | 感知哈希（pHash）比对，防止播放录像 |
| 设备指纹 | 同一设备短时间高频提交 → 风控 |

## 8. 里程碑

| 阶段 | 周期 | 交付物 | 通过标准 |
|---|---|---|---|
| **P0 技术验证** | 1–2 周 | Web 原型 + 离线评测脚本 + 评测集 | 准确率 ≥ 98%（30s/100 次） |
| **P1 可用 MVP** | 2–3 周 | H5：摄像头计数、语音报数、结果页 | 主流机型 30fps、延迟 < 300ms |
| **P2 产品化** | 3–4 周 | 小程序 + 后端 + 账号 + 历史 + 每日目标 | 可完整跑通「跳→存→看」 |
| **P3 增长** | 3–4 周 | 勋章、排行、班级 PK、家长端、防作弊 | 留存/分享数据可测 |
| **P4 进阶** | 4–6 周 | 动作质量分析（膝角、落地缓冲）、多人同屏（切 YOLO-Pose / RTMPose + ByteTrack）、智能跳绳接入 | — |

**团队配置（MVP）**：1 前端/客户端 + 1 算法（可前端兼）+ 1 后端 + 0.5 设计 + 0.5 产品。

**成本**：推理全在端侧，服务器只承担账号/记录/排行，1 万 DAU 月成本通常在几百到几千元量级。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 弱光/逆光识别失败 | 致命 | 引导补光 + 光线质量实时提示 + 灰度校准 |
| 手机摆放角度不当 | 高 | 首次使用做「摆放引导」：全身框、距离条、角度提示 |
| 低端安卓机型帧率不足 | 高 | 模型分级（Lite/Full 按机型下发）、降分辨率、降采样 |
| 模型文件大、首屏慢 | 中 | CDN + 强缓存 + 预加载进度条 |
| 未成年人隐私合规 | 高 | 端侧推理、不上传视频、家长授权、明示隐私政策 |
| 计数争议（家长觉得数少了） | 中 | 提供逐次跳动的波形回放，让家长能看到「哪一次没算」 |

## 10. 验收指标

- **准确率**：30 秒 100 次场景，绝对误差 ≤ 2 次（≥98%）
- **性能**：中端安卓 ≥ 15fps，端到端延迟（跳→报数）< 300ms
- **稳定性**：连续 10 分钟不崩溃、内存不持续增长
- **机型覆盖**：iOS 14+，Android 8+，覆盖 Top 50 机型
- **体验**：首次进入 3 步内开始跳绳

## 11. 如果只做一件事

**先做离线评测集。**

绝大多数跳绳 App 死在这里：Demo 里跳 10 个能数对，真实场景（逆光、远距离、孩子乱跳、手机放歪）就崩了。算法调参必须以**标注好的真实视频回归集**为唯一依据，而不是「我觉得挺准的」。

## 12. 国内落地：阿里云部署要点

> 环境实测：ECS 位于 `cn-hangzhou`。ECS 出网可达 Google CDN，但**终端用户手机能否访问是另一回事**，必须按「国内用户可能完全连不上」来做设计。

### 12.1 最关键的一条：模型和 WASM 必须自托管

MediaPipe 官方示例默认从 `storage.googleapis.com` / `cdn.jsdelivr.net` 拉取 wasm 和 `.task` 模型文件。国内移动网络下这两个域名极不稳定，典型症状是**首次进入永久卡在「加载中」**。

必须改成自托管：

```js
// ❌ 官方示例（国内不可靠）
// const vision = await FilesetResolver.forVisionTasks(".../tasks-vision/wasm");

// ✅ 自托管到 OSS + CDN
const vision = await FilesetResolver.forVisionTasks(
  "https://cdn.yourdomain.com/mediapipe/wasm"
);
const landmarker = await PoseLandmarker.createFromOptions(vision, {
  baseOptions: {
    modelAssetPath: "https://cdn.yourdomain.com/models/pose_landmarker_lite.task",
    delegate: "GPU",
  },
  runningMode: "VIDEO",
  numPoses: 1,
});
```

OSS 上给这两个目录配置长缓存：

```
Cache-Control: public, max-age=31536000, immutable
```

### 12.2 阿里云组件映射

| 用途 | 选型 |
|---|---|
| 模型 / 前端静态资源 | OSS + CDN |
| 后端服务 | ECS（现有）或函数计算 FC |
| 数据库 | RDS PostgreSQL |
| 缓存 / 排行榜 | 云数据库 Tair（Redis） |
| 抽帧证据 | OSS 私有 Bucket + 签名 URL |
| 消息推送 | 短信服务 + 小程序订阅消息 |

### 12.3 小程序侧的域名白名单

微信小程序要求 `request` / `downloadFile` 域名必须预先配置在后台白名单，且必须 **HTTPS + ICP 备案**。模型域名、API 域名、OSS 域名都要提前加，否则真机直接报错——这个坑通常在提测前一天才发现。

### 12.4 WASM 的两个坑

- 多线程 WASM 需要 `Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy` 响应头，OSS 静态站点要单独配置规则
- 小程序 WebView 对 `SharedArrayBuffer` 支持不完整，**建议直接走单线程 + GPU delegate**，别折腾多线程

### 12.5 为什么不用阿里云「人体关键点识别」API

视觉智能开放平台确实有人体关键点能力，但这个场景不合适：

- **按次计费**：30fps 实时流，成本随使用时长线性爆炸
- **延迟**：每帧上传 + 云端推理 + 返回，端到端 < 300ms 基本做不到
- **合规**：未成年人视频持续出端，隐私风险高

**端侧推理做实时计数，云端 API 只用于低频的离线批量复盘**，这个分工不要搞反。
